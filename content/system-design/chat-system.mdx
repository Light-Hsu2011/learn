# 設計聊天系統（Chat System）

<ELI5>
想像你和朋友用對講機聊天：

- **一對一聊天**：你按下按鈕說話，對方的對講機立刻響起。如果對方關機了，你的話會被錄下來，等對方開機再播放
- **群組聊天**：你說一句話，所有同頻道的人都聽到。但如果群組有 500 人，你不可能一個一個打電話通知

WebSocket 就是這個「對講機頻道」— 建立持久連線，伺服器可以主動推訊息給客戶端，不用客戶端一直問「有新訊息嗎？」
</ELI5>

## 問題定義

設計一個支援一對一聊天和群組聊天的即時通訊系統，包含訊息傳遞、離線訊息、已讀回執等功能。

<Callout type="info" title="核心技術選擇">
即時通訊的關鍵是 **WebSocket**：建立持久的雙向連線，伺服器可以主動推送訊息。HTTP 輪詢（Polling）太浪費資源，Long Polling 延遲太高，WebSocket 是最佳方案。
</Callout>

## 需求分析

- **功能性需求**：一對一聊天、群組聊天（最多 500 人）、已讀回執、離線訊息、多裝置同步
- **非功能性需求**：低延遲（< 200ms）、訊息不遺失、訊息順序正確
- **規模估算**：5,000 萬 DAU、每人每天 40 條訊息 = 每日 20 億條訊息
- **連線管理**：每個在線用戶維持一個 WebSocket 連線

## 注意事項

<Callout type="warning" title="群組訊息的扇出問題">
一個 500 人的群組，發一條訊息就要推送給 499 個人。如果每人都在線，就是 499 次 WebSocket 推送。當有多個大群組同時活躍時，推送量會爆炸。必須用 Message Queue 來削峰，並考慮大群組的特殊處理策略。
</Callout>

## 架構設計

### WebSocket 連線管理（TypeScript）

```typescript
// 連線管理器：追蹤哪個用戶在哪台伺服器
class ConnectionManager {
  private connections = new Map<string, WebSocket>(); // userId → ws

  addConnection(userId: string, ws: WebSocket) {
    this.connections.set(userId, ws);
    // 在 Redis 中記錄：userId → serverId
    redis.set(`online:${userId}`, SERVER_ID, "EX", 300);
  }

  removeConnection(userId: string) {
    this.connections.delete(userId);
    redis.del(`online:${userId}`);
  }

  async sendToUser(userId: string, message: ChatMessage) {
    const ws = this.connections.get(userId);
    if (ws?.readyState === WebSocket.OPEN) {
      ws.send(JSON.stringify(message));
      return true;
    }
    return false; // 用戶不在此伺服器或離線
  }
}
```

### 訊息發送流程（C#）

```csharp
public class ChatService
{
    private readonly IMessageQueue _queue;
    private readonly IMessageRepository _repo;
    private readonly IConnectionRegistry _registry;

    public async Task SendMessage(ChatMessage msg)
    {
        // 1. 產生訊息 ID 和時間戳
        msg.Id = Guid.NewGuid().ToString();
        msg.Timestamp = DateTimeOffset.UtcNow;

        // 2. 持久化訊息
        await _repo.SaveAsync(msg);

        // 3. 取得接收者清單
        var recipients = msg.IsGroup
            ? await _repo.GetGroupMembersAsync(msg.GroupId!)
            : new[] { msg.RecipientId! };

        // 4. 逐一推送（透過 MQ 非同步）
        foreach (var recipientId in recipients)
        {
            if (recipientId == msg.SenderId) continue;
            await _queue.PublishAsync("chat.deliver", new DeliveryTask
            {
                MessageId = msg.Id,
                RecipientId = recipientId
            });
        }
    }
}

// MQ Consumer：負責實際推送
public class DeliveryWorker
{
    public async Task HandleDelivery(DeliveryTask task)
    {
        var serverId = await _registry.GetServerIdAsync(task.RecipientId);
        if (serverId != null)
        {
            // 用戶在線：透過該伺服器的 WebSocket 推送
            await _registry.PushToServerAsync(serverId, task);
        }
        else
        {
            // 用戶離線：存入離線訊息表
            await _offlineStore.SaveAsync(task);
        }
    }
}
```

## 實戰補充

<Callout type="tip" title="訊息排序的挑戰">
分散式系統中，訊息的絕對順序很難保證。實務做法：
1. **單聊**：用伺服器端時間戳排序，精度到微秒基本夠用
2. **群聊**：用遞增的 Sequence ID（每個群組獨立的計數器），由 Chat Service 統一分配
3. **跨裝置**：用戶的多裝置間用 Sync Protocol，每個裝置記錄最後同步的 Sequence ID
</Callout>

## 重點整理

<Callout type="tip" title="一句話記住">
**聊天系統 = WebSocket 即時推送 + Message Queue 處理扇出 + 離線訊息表保證不遺失。**
</Callout>

| 概念 | 說明 |
|------|------|
| **WebSocket** | 全雙工持久連線，即時通訊的基礎 |
| **連線映射** | Redis 記錄 userId → serverId，知道推送到哪台伺服器 |
| **Message Queue** | 非同步處理訊息推送，削峰填谷 |
| **離線訊息** | 用戶不在線時暫存訊息，上線後拉取 |
| **Sequence ID** | 每個對話/群組的遞增序號，確保訊息順序 |
