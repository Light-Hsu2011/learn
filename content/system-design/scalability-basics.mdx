# 可擴展性基礎（Scalability Basics）

<ELI5>
想像你開了一家小餐廳，生意越來越好：

- **垂直擴展（Scale Up）**：把廚房換成超大的，買最頂級的爐具 — 一個廚師變成超級廚師
- **水平擴展（Scale Out）**：開分店！每家分店都能接客，客人被分散到不同分店

垂直擴展就像把一個人練成超人，但超人也有極限。水平擴展就像組一支軍隊，人數可以一直加。現代大型系統幾乎都選擇水平擴展，因為沒有一台機器能無限升級。
</ELI5>

## 是什麼？

Scalability（可擴展性）是系統在負載增加時，透過增加資源來維持效能的能力。一個可擴展的系統不會因為用戶從 1,000 變成 1,000,000 就掛掉。

<Callout type="info" title="核心區分">
**Scale Up（垂直擴展）**：升級單一機器的 CPU、RAM、SSD。簡單但有上限。
**Scale Out（水平擴展）**：增加更多機器，透過分散負載來處理更多請求。複雜但幾乎無上限。
</Callout>

## 核心觀念

- **Stateless Design**：伺服器不保存用戶狀態，任何請求可以被任何伺服器處理，這是水平擴展的前提
- **CAP 定理**：分散式系統只能同時滿足 Consistency、Availability、Partition Tolerance 中的兩個
- **Throughput vs Latency**：擴展目標是提高 throughput（吞吐量）同時維持 latency（延遲）
- **Elasticity**：系統根據負載自動增減資源的能力（Auto Scaling）
- **Single Point of Failure（SPOF）**：任何只有一個的元件都是風險，水平擴展天然避免 SPOF

## 常見誤區

<Callout type="warning" title="不要一開始就過度設計">
Premature optimization is the root of all evil。先確認瓶頸在哪，再決定擴展策略。很多系統在 Scale Up 就能解決問題的階段，不需要急著做 Scale Out 帶來的複雜度。
</Callout>

## 架構設計

### Stateless 改造範例（C#）

```csharp
// 不好的做法：狀態存在伺服器記憶體
public class CartController : Controller
{
    private static Dictionary<string, List<Item>> _carts = new(); // 會死在 Scale Out

    [HttpPost("add")]
    public IActionResult Add(string userId, Item item)
    {
        if (!_carts.ContainsKey(userId)) _carts[userId] = new();
        _carts[userId].Add(item);
        return Ok();
    }
}

// 正確做法：狀態放到外部儲存
public class CartController : Controller
{
    private readonly IDistributedCache _cache;

    public CartController(IDistributedCache cache) => _cache = cache;

    [HttpPost("add")]
    public async Task<IActionResult> Add(string userId, Item item)
    {
        var cart = await _cache.GetAsync<List<Item>>(userId) ?? new();
        cart.Add(item);
        await _cache.SetAsync(userId, cart, TimeSpan.FromHours(1));
        return Ok();
    }
}
```

// CP 系統：選擇一致性 + 分區容錯，犧牲可用性
// 例如：ZooKeeper、etcd — 金融交易場景
// 當網路分區發生時，寧可拒絕請求也不回傳舊資料

// 例如：Cassandra、DynamoDB — 社群媒體場景

## 實戰補充

<Callout type="tip" title="面試技巧">
System Design 面試中，面試官問「這系統怎麼擴展？」時，先回答三件事：
1. **哪裡是瓶頸**（讀多還是寫多？CPU bound 還是 IO bound？）
2. **Stateless 嗎**（如果不是，怎麼改造？）
3. **CAP 取捨**（你的場景更在意一致性還是可用性？）
這三個問題回答完，後續的具體技術方案自然就出來了。
</Callout>

## 重點整理

<Callout type="tip" title="一句話記住">
**Scalability = Stateless + Load Balancer + CAP 取捨，先找瓶頸再決定 Scale Up 還是 Scale Out。**
</Callout>

| 概念 | 說明 |
|------|------|
| **Scale Up** | 升級單機硬體，簡單但有天花板 |
| **Scale Out** | 增加機器數量，複雜但幾乎無上限 |
| **Stateless Design** | 伺服器不存狀態，水平擴展的必要前提 |
| **CAP 定理** | 分散式系統只能三選二：一致性、可用性、分區容錯 |
| **Auto Scaling** | 根據監控指標自動增減機器數量 |
